# 做四足 RL 时踩过的 25 个坑

> 全部是**我自己的 bug**，不是框架的锅。
>
> 写这份文档的原因很简单：这些坑没有一个写在论文里，也很少有教程提。
> 每一个都花了我半天到两天，症状还都长得很像"策略不行"。
>
> 如果你正在做 sim2sim 或者换仿真器复现策略，**这份清单能帮你省掉其中大部分时间**。

---

## 为什么这些坑特别难发现

因为它们**看起来都像策略问题**：

- 步态突然抖动 → 你会去调奖励、调 domain randomization
- 机器人走两步就摔 → 你会怀疑训练不够
- 通过率异常高 → 你会以为策略很好

真正的原因是：**你测的东西不是你以为在测的东西。**

## 一、测量类（8 个）

| # | 错误 | 正确做法 |
| --- | --- | --- |
| 1 | 用 `mj_objectVelocity(flg_local=1)` 取体坐标系角速度 | **它返回的是取反值**。自由关节的 `qvel[3:6]` 本身就是体坐标系角速度，直接用 |
| 2 | 把 IsaacGym 的四元数 `(x,y,z,w)` 直接赋给 MuJoCo 的 `(w,x,y,z)` | 必须换序。不换等于凭空偏航 180° |
| 3 | 以为 MuJoCo 自由关节的 `qvel[0:3]` 是体坐标系 | **是全局系**。体坐标系要 `R.T @ qvel[0:3]` |
| 4 | 用 `vars(cls)` 读配置 | **不遍历继承链**，读不到父类字段。要用 MRO |
| 5 | 用关节原点速度测接地点打滑 | 原点不动但足端在滑。要用接触点速度 `v + ω×r` 或雅可比 |
| 6 | 以为固定的足关节会被 MuJoCo 合并 | 自己写的 MJCF 里它们**独立存在**；但 URDF 导入器会合并。两条路径行为不一致 |
| 7 | 回放动作时没关延迟随机化 | 开了延迟时，**记录下来的动作 ≠ 实际施加的动作**，回放必然对不上 |
| 8 | 忘了训练时 `randomize_pd_gain` 是开的 | 实际增益是标称值 × (0.9~1.17)，不是标称值 |

**这一类有个共同点：数值看起来"差不多对"，所以你不会去查。**

## 二、建模类（4 个）

| # | 错误 | 后果 / 正确做法 |
| --- | --- | --- |
| 9 | 从**当前模型**反推基准质量 / 质心 | `base_mass0 = 质量 − 偏移`，再加回偏移会**自我抵消**，等于没改。要用 pristine 缓存 |
| 10 | `<inertial>` 同时给 `quat` 和 `fullinertia` | MuJoCo 不允许。要把惯量**旋进连杆坐标系**再用 `fullinertia` |
| 11 | 碰撞几何体重名 | MuJoCo 直接报错。多车道场景要**去掉 name** |
| 12 | 临时 XML 写在 `/tmp` | `meshdir` 是相对路径，**必须写在工程目录里** |

## 三、逻辑类（13 个，最隐蔽）

| # | 错误 | 后果 |
| --- | --- | --- |
| 13 | **多个脚本各自建模型，有的忘了注入同一套物理参数** | 症状都是"步态突然剧烈抖动"。**我犯了 3 次**。最后用统一的 `load_scene()` 封死 |
| 14 | 相机每帧覆写 `cam.lookat` | 用户没法平移视角，感觉"视角锁死" |
| 15 | 判摔用**世界坐标绝对高度** `z < 0.12` | **任何下行地形都是错的**：下坡走 5 m，地面已经降到 −0.87 m，正常走路会被判成摔倒。必须用**相对脚下局部地面**的高度 |
| 16 | 单点射线求地面高度 | 相邻瓦片共享面，射线会从缝里漏过去（返回"无地面"）→ 误判掉出世界。要 **5 点十字采样取最高** + 瓦片 2% 重叠 |
| 17 | 沟底 / 坑底顶面放在 `z = 0` | 和地面齐平 → **地形退化成平地**，跑出 100% 通过，但什么都没测到 |
| 18 | `step_down:H` 的顶面放在 `−H + 0.10` | 实际只降了 (H−10) cm，测的不是标注的台阶高度 |
| 19 | 侧向斜坡的中心偏移套用纵向公式 | 在 y=0 处把地面压到 −0.69 m → 10°/15°/20° 三档结果完全相同 |
| 20 | 通过距离的标定基线只有 1.0 m | **原地卡住也算 100%**：只走 1.08 m 的台阶显示"通过" |
| 21 | 两套测试用同一个 `--tag` | **互相覆盖结果文件**，还以为在对比 |
| 22 | 只看 `fell / didn't fall` | 太平庸——**"原地不动"也不会摔**。必须看通过距离和分项指标 |
| 23 | 多车道场景把相机近裁剪面顶到 4.7 m | **一直黑屏**：45 条车道让场景 extent 到 ~470 m，MuJoCo 的 `znear` 按 extent 缩放，于是近裁剪面 4.7 m > 跟随相机距离 1.6 m，机器人和脚下地面整块被裁掉。**HUD 数字照常跳动、地形看起来"就是暗的"**，极易蒙混过关。修：`vis.map.znear=1e-5`、`zfar=1.0` |
| 24 | 对比脚本只认 `fell` 字段 | 地形套件写的是 `fell_at`，进度是 `reach_frac`。第一次比就 `KeyError`；更糟的是即使不崩，**进度也从没被监视过**——一条地形从"走 6 m"退化成"卡在 1 m"会被报成"没有变化" |
| 25 | 执行器限值 / 负载在三套测试里各有各的写法 | 三个套件各自建模型，其中一处还**硬编码了一份扭矩限值**；负载因为"模型被整个换掉"而三处全部丢失。症状：`PAYLOAD=0` 和 `PAYLOAD=5` 的结果**逐位相同**，怎么调都一样。**白跑了 7 轮 A/B** |

## 元教训：先后悔，再交付

25 个 bug 里有 **15 个是"报告了一个数字之后才发现测量方法错了"**。

第 23 号更狠：**它连数字都不给**，只是安静地什么都不画——如果你不去看渲染出的像素，
永远不会发现。

### 三条可以立刻用上的自检规则

1. **新写的诊断脚本，先用"已知答案"的简单场景自检。**
   例：平地站立时，脚端速度应该约等于 0。跑出来不是 0，先怀疑测量，别怀疑策略。

2. **任何"应该生效"的旋钮，都要做一次 0 vs 非 0 的结果 diff。**
   两份结果一模一样，就是没接上。这条能直接挡掉第 25 号坑。

3. **比"摔没摔"更弱的指标不要当结论。**
   原地不动也能"不摔"，站着不动也能"没超时"。

## 顺带：一个反例，说明"配置 ≠ 实际"

训练时关掉 `push_robots` 并不等于关掉了整个 domain randomization。
**其余随机化在播放时全部生效。**

| 参数 | 训练时实际值 | 配置文件标称值 |
| --- | --- | --- |
| **关节阻尼** | **1.088** | 0 |
| 地面摩擦 | **0.633** | 1.0 |
| 机身附加质量 | −0.593 kg | 0 |
| armature | 0.005 | 0 |

按标称值搭模型，腿会欠阻尼到**脚在地面上打颤蹭地**，步态完全不对。

加上这些之后：打滑 0.808 → 0.086 m/s，高度标准差 0.0316 → 0.0037，速度跟踪 0.213 → 0.481（指令 0.5）。

**正确做法是从训练环境里把真实参数 dump 出来，而不是读配置文件。**
